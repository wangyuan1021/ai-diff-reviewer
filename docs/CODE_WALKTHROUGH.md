# AI Diff Reviewer 代码导读、学习路线与面试题

本文面向两类读者：

- 希望快速读懂本项目，并能继续开发的人。
- 希望把项目用于简历讲解、技术面试和系统设计讨论的人。

建议不要从头逐行阅读。先跑通一条完整链路，再沿数据流进入各模块，最后结合测试理解边界条件。

## 一、30 秒理解项目

AI Diff Reviewer 是一个隐私优先的 Git Diff 风险审查工具。它接收 Unified Diff，先通过确定性本地规则发现依赖、配置、权限、迁移、动态执行、硬编码敏感信息等风险；如果选择 AI 模式，再对 Diff 分块、脱敏并匿名化文件路径，交给可替换的 AI Provider 分析。模型输出必须经过 Schema、文件路径和行号三层校验，最终与本地规则合并。

审查通过异步任务执行，浏览器用 SSE 接收进度。实时结果会短暂保存在内存中，隐私化后的历史摘要与结构化结果写入 SQLite；原始 Diff、hunk 和风险代码证据不会持久化。

一句话概括核心设计：

> 用确定性规则兜底，用受约束的 AI 扩展能力，并在进入模型、接受模型输出和写入历史三个位置建立安全边界。

## 二、技术栈与模块边界

| 模块                   | 技术                         | 主要职责                                      |
| ---------------------- | ---------------------------- | --------------------------------------------- |
| `apps/web`             | Vue 3、TypeScript、Vite      | Diff 输入、模式选择、SSE 进度、结果和历史展示 |
| `apps/server`          | Node.js 22、Koa、Zod、SQLite | API、任务状态、Provider、AI 编排、历史与导出  |
| `packages/diff-engine` | TypeScript、`parse-diff`     | Diff 解析、规则引擎、分块、敏感信息检测与脱敏 |
| `packages/shared`      | TypeScript                   | 前后端共享领域模型和 API 类型                 |
| `evaluation`           | 虚构 Diff 样本               | 确定性评测规则召回、意外命中和脱敏类型召回    |
| `deploy`、`Dockerfile` | Nginx、Docker                | 同源反向代理、SSE 支持、容器化运行            |

依赖方向保持为：

```text
apps/web ───────────────┐
                       ├──> packages/shared
apps/server ────────────┤
       └──> packages/diff-engine ──> packages/shared
```

`diff-engine` 不依赖 Web、数据库或网络，因此可以独立测试和复用。`shared` 只定义类型，不承载业务逻辑。

## 三、先看完整调用链

以页面选择 Mock AI 并提交 Diff 为例：

```text
App.vue
  │ POST /api/review-tasks
  ▼
Koa app.ts
  │ 创建任务，立即返回 202 + taskId
  ▼
ReviewTaskManager
  ├─ parseUnifiedDiff()
  ├─ runLocalRules()
  ├─ redactParsedDiff()
  ├─ createReviewChunkPlan()
  ├─ Mock/OpenAI/Ollama Provider
  ├─ Schema + 文件 + 行号校验
  ├─ 合并本地与 AI 风险
  └─ 保存隐私化历史，生成独立 historyId
  │
  ├─ SSE 推送任务快照 ──> App.vue 展示实时结果
  └─ SQLite 历史 ───────> 历史详情与 Markdown 导出
```

这里有两个不同的 ID：

- `taskId` 用于查询、订阅和取消内存任务。
- `historyId` 用于读取持久化历史和下载报告。

两个 ID 独立生成，防止从历史列表拿到 ID 后，在任务保留期内反查包含实时代码证据的任务结果。

## 四、推荐阅读顺序

### 1. 从共享模型建立领域词汇

先读 `packages/shared/src/index.ts`。

重点类型：

- `ParsedDiff`、`ChangedFile`、`DiffHunk`、`DiffLine`：Diff 的内存表示。
- `ReviewRisk`：本地规则与 AI 统一使用的风险结构。
- `LocalReviewResult`、`AIReviewResult`：两类审查结果。
- `ReviewTaskSnapshot`：异步任务对外暴露的状态快照。
- `ReviewHistorySummary`、`ReviewHistoryDetail`：持久化历史模型。

值得注意的设计：

- `source` 表示当前风险来自本地、AI 或二者合并。
- `sources` 保留原始来源集合，避免合并后丢失可解释性。
- `AIReviewMetadata.coverage` 明确记录大 Diff 是否被截断，而不是假装完成了全量审查。
- `AIReviewMetadata.redaction` 记录脱敏数量与类型，让隐私处理对用户可见。

### 2. 理解 Diff 如何变成结构化数据

阅读 `packages/diff-engine/src/parser.ts`。

核心步骤：

1. 拒绝空输入。
2. 按 UTF-8 字节数限制 Diff 大小，而不是用字符串字符数代替。
3. 粗校验 Unified Diff 标志。
4. 使用 `parse-diff` 解析文件和 hunk。
5. 规范化 `a/`、`b/` 与 `/dev/null` 路径。
6. 推断新增、修改、删除和重命名类型。
7. 生成文件数、新增行、删除行等统计。

阅读时回答：为什么删除行只有 `oldLine`，新增行只有 `newLine`？为什么 AI 风险最终只接受有效的新文件行号？

### 3. 理解本地规则为什么是系统基线

阅读 `packages/diff-engine/src/rules.ts`。

规则分为两类：

- 文件级规则：依赖、配置、数据库迁移、认证权限、公共 API、大文件变更。
- 行级规则：动态代码执行、硬编码秘密、个人或内部信息、TODO、调试输出、异常处理删除。

本地规则的价值不是替代人工审查，而是提供：

- 确定性：相同输入得到相同结果。
- 可测试性：每条规则都有稳定的 `ruleId`。
- 低成本：不需要网络和模型费用。
- AI 兜底：Provider 不可用或预算不足时仍有结果。

规则的主要局限是正则和路径启发式会产生误报、漏报，无法理解跨文件语义或业务上下文。

### 4. 理解隐私处理的两层含义

阅读 `packages/diff-engine/src/sensitive.ts` 和对应测试。

系统处理两类隐私：

- 值脱敏：凭据、Bearer/JWT 类令牌、私钥、连接串、邮箱、私网 IP。
- 路径匿名化：真实文件路径映射为 `FILE_001`、`FILE_002`。

敏感值使用类型占位符替换，例如保留“这里存在凭据”的语义，但不把真实值发送给 Provider。多行私钥需要整体识别，不能逐行处理后泄露中间内容。

安全边界需要诚实描述：基于模式的扫描只能降低泄露概率，无法保证识别任意秘密，因此外部 Provider 仍需要遵守组织的数据分类策略。

### 5. 理解大 Diff 的预算控制

阅读 `packages/diff-engine/src/chunker.ts`。

分块策略：

- 以文件和 hunk 为基本单位。
- 超大 hunk 继续按行拆分。
- 配置、依赖、认证权限和迁移文件优先。
- 在字符预算内选择分块，记录未覆盖文件、分块和省略字符数。

当前实现用字符数近似模型上下文，不是精确 Token 计数。它简单、Provider 无关，但不同语言和模型下误差较大，是后续可优化点。

### 6. 理解 Provider 适配层

阅读 `apps/server/src/ai/providers.ts`。

三个 Provider 共享 `AIProvider` 接口：

- `MockProvider`：返回固定、可重复的结构化响应，不是真实模型。
- `OpenAICompatibleProvider`：调用 `/chat/completions`，使用 JSON Object 响应格式。
- `OllamaProvider`：调用本机或自托管的 `/api/chat`。

适配层统一处理：

- 模型名称。
- 超时。
- 父级取消信号。
- 网络、上游 HTTP 和响应格式错误。

增加新 Provider 时，应实现相同接口，而不应把厂商判断散落到审查主流程。

### 7. 精读 AI 审查主流程

`apps/server/src/ai/review.ts` 是整个项目最值得精读的文件。

完整步骤：

1. 解析 Diff 并运行本地规则。
2. 脱敏结构化 Diff。
3. 建立真实路径与匿名 ID 的双向映射。
4. 按预算生成分块，并匿名化分块 ID 与路径。
5. 拼装系统消息、文件统计、本地规则证据和 Diff 分块。
6. 对最终 Prompt 再执行一次真实路径全量替换。
7. 调用 Provider。
8. 用严格 Zod Schema 校验模型 JSON；失败时只修复重试一次。
9. 验证每条 AI 风险的匿名文件 ID和新文件行号确实存在于已发送分块。
10. 恢复本地真实路径。
11. 合并本地与 AI 风险，生成覆盖率、脱敏和耗时元数据。

模型输出不能直接信任。这里的校验分为：

| 层次       | 防止的问题                                 |
| ---------- | ------------------------------------------ |
| JSON 解析  | 模型返回 Markdown 或非法 JSON              |
| Zod Schema | 字段缺失、类型错误、文本过长、风险数量失控 |
| 文件白名单 | 模型引用未发送或不存在的文件               |
| 行号白名单 | 模型伪造证据位置                           |

即使通过这些校验，也只代表“格式和引用有效”，不代表风险结论一定正确，因此页面仍强调人工复核。

### 8. 理解异步任务状态机

阅读 `apps/server/src/tasks.ts`。

状态流转：

```text
queued → running → completed
                 ↘ failed
                 ↘ cancelled
                 ↘ timed-out
```

关键实现：

- `setImmediate` 让创建接口先返回 `202`，再执行任务。
- `AbortController` 把用户取消和任务超时传递到外部 HTTP 请求。
- 监听器集合向 SSE 路由发布不可变任务快照。
- 终态任务保留一段时间，支持短暂断线后查询。
- 完成后生成独立 `historyId`，写历史成功后才发布完成状态。
- 清理定时器调用 `unref()`，避免它阻止 Node.js 进程退出。

当前任务队列只存在单进程内存中，因此不支持多实例共享、进程重启恢复或可靠重试。这是 MVP 的明确边界。

### 9. 理解 API 与 SSE

阅读 `apps/server/src/app.ts`。

主要接口：

| 方法与路径                         | 作用               |
| ---------------------------------- | ------------------ |
| `GET /api/health`                  | 健康检查           |
| `POST /api/reviews/local`          | 同步本地规则审查   |
| `POST /api/reviews/ai`             | 同步联合审查       |
| `POST /api/review-tasks`           | 创建异步任务       |
| `GET /api/review-tasks/:id`        | 查询任务快照       |
| `GET /api/review-tasks/:id/events` | 订阅 SSE 进度      |
| `DELETE /api/review-tasks/:id`     | 取消任务           |
| `GET /api/history`                 | 分页读取历史摘要   |
| `GET /api/history/:id`             | 读取隐私化历史详情 |
| `GET /api/history/:id/markdown`    | 下载 Markdown 报告 |

SSE 适合本项目，因为通信主要是服务端单向推送，浏览器原生支持 `EventSource`，比 WebSocket 更轻。服务端每 15 秒写入 heartbeat，Nginx 关闭代理缓冲，避免进度事件积压。

全局错误处理中区分输入错误、Provider 错误和未知错误；未知错误不把内部堆栈返回给客户端。

### 10. 理解历史持久化边界

阅读 `apps/server/src/history.ts` 和 `apps/server/src/markdown.ts`。

写入 SQLite 前会：

- 深拷贝结果。
- 清空所有 hunk。
- 替换结构化文本中出现的原始变更行。
- 将所有风险 `evidence` 统一替换为隐私提示。
- 只保存 Diff 的 SHA-256，而不是原始 Diff。

为什么风险证据直接统一替换？因为规则证据可能先被截断，截断后的字符串不再等于完整原始行，单纯依赖精确字符串替换可能漏掉代码片段。

SQLite 使用 Node.js 22 内置同步 API。对本地单用户 MVP，它减少了依赖和复杂度；在高并发服务中，同步数据库操作会阻塞事件循环，应替换为异步数据库客户端或独立持久化服务。

### 11. 理解前端状态流

阅读 `apps/web/src/App.vue`。

核心状态只有几组：

- `diff`：用户输入。
- `reviewMode`：本地、Mock、OpenAI-compatible 或 Ollama。
- `task`：任务进度与终态。
- `result`：当前显示的实时或历史结果。
- `history`、`selectedHistory`：历史列表与详情。

页面提交任务后创建 `EventSource`。收到终态快照时关闭连接、展示结果并刷新历史。组件卸载时也会关闭连接，防止资源泄漏。

当前所有页面逻辑集中在单个 `App.vue`，适合小型演示，但继续扩展时应拆分为：输入面板、任务进度、结果卡片、历史面板，以及 `useReviewTask`、`useHistory` 等组合式函数。

### 12. 理解质量保障与部署

按以下顺序阅读：

1. 各模块旁边的 `*.test.ts`。
2. `evaluation/manifest.json` 与 `scripts/evaluate.ts`。
3. `scripts/smoke-test.mjs`。
4. `.github/workflows/ci.yml`。
5. `Dockerfile`、`compose.yaml`、`deploy/nginx.conf`。

项目有三类验证：

- 单元/接口测试：解析、规则、脱敏、Provider、AI 校验、任务、历史和 API。
- 确定性评测：16 个虚构样本验证规则集合和敏感类型。
- 生产 bundle 冒烟：把构建后的 Server bundle 复制到隔离目录，验证它不依赖仓库 `node_modules` 也能完成真实 HTTP 流程。

CI 还会验证生成的评测报告没有漂移，并构建 Server 与 Web 两个镜像目标。

## 五、七阶段学习路线

每个阶段建议控制在 1～2 小时，先动手再总结。

### 阶段 1：跑通系统并建立地图

目标：知道用户操作如何对应网络请求和源码入口。

实践：

1. 运行 `pnpm dev`。
2. 用默认样例分别执行“本地规则”和“Mock AI”。
3. 在浏览器网络面板观察创建任务、SSE 和历史请求。
4. 对照 `App.vue`、`app.ts`、`tasks.ts` 画出自己的时序图。

自测问题：为什么创建任务返回 `202` 而不是 `200`？为什么页面默认用异步接口而仍保留同步接口？

### 阶段 2：掌握 Unified Diff 与规则引擎

目标：能解释行号、hunk、文件状态和规则证据如何产生。

实践：

1. 阅读 parser 与 rules 测试。
2. 新建一个完全虚构的 Diff，覆盖重命名和删除文件。
3. 增加一条简单规则及测试。
4. 观察新增规则是否影响评测中的“意外规则命中”。

自测问题：规则是应该匹配整个文件文本，还是只匹配新增行？各自会产生什么误报？

### 阶段 3：掌握敏感信息与 Prompt 安全

目标：理解发送外部模型前的数据最小化。

实践：

1. 阅读敏感信息检测测试。
2. 构造包含虚构令牌、邮箱、私网 IP 和私钥的 Diff。
3. 在测试 Provider 中捕获 Prompt，确认值和真实路径均不存在。
4. 思考正则无法可靠识别的秘密形式。

自测问题：为什么只替换 Diff 头部路径不够？为什么脱敏后的占位符应保留类型语义？

### 阶段 4：掌握不可信模型输出治理

目标：理解 LLM 输出为何必须按外部不可信输入处理。

实践：

1. 让测试 Provider 返回非法 JSON。
2. 返回 Schema 正确但文件不存在的风险。
3. 返回文件正确但行号未发送给模型的风险。
4. 观察修复重试、风险过滤和 warning。

自测问题：Zod 校验通过后，为什么仍要校验文件和行号？

### 阶段 5：掌握异步任务、取消与 SSE

目标：能够讲清状态机、取消传播和连接生命周期。

实践：

1. 阅读 `tasks.test.ts` 和 SSE 接口测试。
2. 把 Mock Provider 临时改为延迟响应，测试取消和超时。
3. 在 SSE 途中刷新页面，再通过任务查询接口观察保留期。
4. 分析任务完成和历史保存的先后顺序。

自测问题：如果先发布完成事件再写数据库，用户可能看到什么竞态？

### 阶段 6：掌握持久化与隐私边界

目标：区分实时数据、持久化数据和导出数据。

实践：

1. 阅读 history 的隐私回归测试。
2. 比较实时结果与历史详情中的 hunk 和 evidence。
3. 下载 Markdown 并搜索虚构原始代码标记。
4. 解释 taskId 与 historyId 分离的威胁模型。

自测问题：只做到“不保存原始 Diff”为什么还不够？

### 阶段 7：掌握工程化交付

目标：能从开发、测试讲到构建、部署和演进。

实践：

1. 运行 `pnpm check` 和 `pnpm eval`。
2. 阅读生产 bundle 冒烟脚本。
3. 解释多阶段镜像如何减少运行时内容。
4. 解释 Nginx 为什么要关闭 API 代理缓冲。
5. 列出从本地 MVP 到团队服务必须补齐的能力。

自测问题：单元测试、评测和冒烟测试分别防止什么回归？

## 六、面试项目介绍模板

### 30 秒版本

> 我做了一个隐私优先的 Git Diff 审查工具。它先用本地确定性规则发现常见工程和安全风险，再把经过分块、敏感值脱敏和文件路径匿名化的最小内容交给可替换的 AI Provider。模型输出会经过严格 Schema、文件白名单和行号白名单校验，再与本地风险合并。系统使用 Koa 异步任务和 SSE 展示实时进度，SQLite 只保存脱敏后的结构化历史，配套有 39 项测试、16 个确定性评测样本、生产 bundle 冒烟和容器化 CI。

### 2 分钟版本

> 这个项目解决两个问题：第一，纯规则审查覆盖有限；第二，直接把代码交给大模型存在隐私和幻觉风险。因此我采用混合架构：本地规则提供确定性基线，AI 负责补充语义分析。
>
> 输入是 Unified Diff。系统先解析文件、hunk 和新旧行号，执行配置、依赖、权限、迁移、动态执行、敏感信息等规则。AI 路径会按文件和 hunk 分块，优先高风险文件，并记录覆盖率。发送前会替换凭据、令牌、私钥、连接串、邮箱和私网 IP，同时把真实路径映射成匿名 ID。
>
> 我不信任模型输出：先用 Zod 校验严格 JSON，再确认风险引用的文件和行号确实出现在已发送分块中，不符合的结果直接过滤。任务通过 SSE 推送进度，AbortController 支持取消和全流程超时。实时结果只在内存保留 15 分钟；历史写入前移除 hunk、替换风险证据，并使用独立历史 ID。
>
> 工程上使用 pnpm monorepo、Vue、Koa、Node 内置 SQLite、Vitest、Supertest、Docker 和 GitHub Actions。当前定位是单机 MVP，下一步会优先补鉴权限流、持久任务队列、多实例一致性和真实模型质量评测。

## 七、常见面试问题与参考答案

答案应结合自己的实际工作表达，不建议逐字背诵。

### 架构与设计

#### 1. 为什么采用本地规则加 AI，而不是只用大模型？

本地规则便宜、稳定、可解释，适合动态执行、敏感凭据、配置和迁移等明确模式；AI 更适合补充上下文和语义风险。两者组合后，即使 Provider 不可用或预算不足，系统仍能返回基础结果；同时 AI 结果也能与确定性证据交叉验证。

#### 2. 为什么使用 monorepo？

前端、服务端和 Diff 引擎需要共享领域类型。pnpm workspace 可以统一依赖、脚本和 TypeScript 配置，并通过 `workspace:*` 保证本地包版本一致。代价是构建顺序和边界管理更复杂，所以项目固定先构建 shared、diff-engine，再构建 apps。

#### 3. 为什么把 diff-engine 做成独立包？

解析、规则、分块和脱敏都是纯本地领域逻辑，不应依赖 HTTP、数据库或 Vue。独立包让它更容易测试、复用，也使网络和持久化副作用集中在 Server。

#### 4. 为什么保留同步 API，又增加异步任务 API？

同步 API 方便脚本调用和向后兼容。页面使用异步 API，是因为外部模型可能耗时数十秒，需要进度、取消和独立超时。两套 API 共享相同的审查核心，避免复制业务逻辑。

#### 5. 为什么选择 SSE 而不是 WebSocket？

业务主要是服务端向浏览器单向推送任务状态，SSE 已足够，并且浏览器原生支持自动重连、实现和代理配置更简单。WebSocket 更适合高频双向通信，这里会增加不必要复杂度。

#### 6. 为什么任务存在内存而历史存在 SQLite？

任务快照包含实时证据，只需要短期支持进度和断线查询；历史需要长期保存，但必须经过隐私化。把二者分开能减少敏感实时数据的持久化范围。缺点是进程重启会丢失运行任务，也不能直接横向扩容。

#### 7. taskId 和 historyId 为什么要分开？

任务接口在保留期内可能返回带原始证据的实时结果，而历史 ID 会出现在历史列表。如果复用同一 ID，拿到历史 ID 的访问者可以尝试读取对应任务。独立随机 ID 降低了跨资源枚举和关联泄露风险，但真正多用户部署仍必须增加鉴权与资源所有权检查。

### Diff、规则与数据模型

#### 8. 如何保证 AI 给出的行号可信？

分块时记录每个匿名文件实际发送的新文件行号集合。模型返回后，先把匿名文件 ID映射回真实路径，再检查该行号是否存在于对应已发送分块；不满足条件的风险直接过滤并产生 warning。

#### 9. 为什么只接受新文件行号？

审查结果主要面向修改后的代码定位，新增或上下文行的新文件行号能直接对应 PR 右侧视图。删除行没有新文件位置，需要单独的数据模型和展示方式；当前 MVP 通过本地规则处理删除异常代码，但 AI 风险协议保持简单。

#### 10. 本地规则如何避免泄露硬编码秘密？

规则先调用统一敏感信息扫描器，只根据命中的类型生成风险，evidence 使用固定说明，不回显原值。这样即使风险显示、日志或历史被读取，也不会因为“报告问题”再次传播秘密。

#### 11. 如何计算总体风险？

项目按 `low < medium < high < critical` 取所有合并风险中的最高等级。它直观且容易解释，但没有考虑风险数量、置信度或文件重要性；生产系统可改为可配置评分模型，同时保留最高严重项兜底。

#### 12. 本地与 AI 风险如何去重？

当前使用文件、类别、行号和标准化标题做精确匹配。命中后标记为 `combined` 并合并证据。这个策略确定性强，但对同义标题不敏感；后续可采用规范化规则标签、文本相似度或模型辅助聚类。

#### 13. 大 Diff 如何处理？

先按文件/hunk 分块，超大 hunk 再按行拆分；高风险路径优先进入字符预算。结果中明确返回总分块、已审查分块、跳过文件和省略字符数，让用户知道覆盖不完整。

#### 14. 为什么不用直接截断整个 Prompt？

直接截断可能切断 hunk、丢失行号或只覆盖前几个普通文件。结构化分块可以保持证据完整，并用优先级优先审查权限、配置、依赖和迁移等高影响区域。

### AI 与安全

#### 15. Mock AI 是什么模型？

它不是模型，而是返回固定合法 JSON 的测试替身，默认显示名为 `mock-reviewer-v1`。它用于无密钥演示、接口测试、SSE 和持久化流程验证，不能代表真实 AI 的代码理解能力。

#### 16. 如何适配不同模型供应商？

所有 Provider 实现统一的 `AIProvider.complete()` 接口，输入是消息、回退文件/行号和取消信号，输出是文本与实际模型名。审查编排只依赖接口，不依赖具体厂商。当前提供 OpenAI-compatible 和 Ollama 两种协议。

#### 17. 如何处理模型返回非法 JSON？

第一次响应先做 JSON 和严格 Zod 校验。失败后追加一条仅要求按原 Schema 重写 JSON 的消息，再调用一次；第二次仍失败就返回结构化 `AI_RESPONSE_INVALID`，不无限重试。

#### 18. 为什么 Schema 校验还不够？

Schema 只能保证结构正确，不能保证引用事实存在。模型完全可能返回格式合法但虚构的文件和行号，所以还需要基于实际发送分块的文件与行号白名单校验。

#### 19. 如何防止代码或路径泄露给外部模型？

系统只发送预算内的必要分块；先替换敏感值，再把路径映射为匿名 ID，并在最终 Prompt 拼装后全量替换所有已知新旧路径。API Key 只存在服务端环境变量中。需要强调，这些是风险降低措施，不是绝对的数据防泄漏证明。

#### 20. 如何应对 Prompt Injection？

Diff 中的文本被作为不可信审查材料，系统消息要求只根据证据输出固定 JSON；更重要的是，模型输出必须经过 Schema、文件和行号校验，不能直接触发工具或写操作。当前系统没有 Agent 工具调用，因此注入影响主要限于审查文本质量。后续仍可增加输入边界标记、指令冲突测试和输出内容策略。

#### 21. 为什么 temperature 设置为 0？

代码审查更关注稳定性和可复现性，低随机性便于调试和比较结果。但 temperature 0 也不保证跨请求绝对一致，模型版本和服务端实现仍可能变化。

#### 22. 如何评价这个 AI 功能的质量？

当前 `pnpm eval` 只确定性评测本地规则与脱敏，不评价真实模型输出。真实 AI 评测应建立冻结样本、专家标注、风险级别与证据定位指标，并分别统计准确率、召回率、误报率、行号有效率、成本和延迟；还要固定模型版本和 Prompt 版本。

### 异步、后端与可靠性

#### 23. 取消是如何传递到模型请求的？

每个任务持有 `AbortController`。用户取消或任务超时时调用 `abort()`，signal 传入审查函数，再传入 Provider 的 `fetch`。Provider 还创建自己的超时 controller，并监听父 signal，从而同时支持请求级超时和任务级取消。

#### 24. Provider 超时和任务总超时有什么区别？

Provider 超时限制单次外部 HTTP 调用；任务总超时覆盖解析、本地规则、可能的修复重试、Provider 调用和保存全过程。两者分别保护外部依赖和端到端用户体验。

#### 25. SSE 连接中断后怎么办？

当前页面提示连接中断，任务仍在服务端继续执行，保留期内可通过任务查询接口获取快照。更完善的实现应记录最后事件 ID、自动回退轮询或在重连后立即查询任务状态。

#### 26. 为什么保存历史后才把任务标记为 completed？

这样客户端收到完成事件并刷新历史时，记录已经存在，避免“任务完成但历史暂时 404”的竞态。如果保存失败，任务应进入 failed，而不是对外宣称完成。

#### 27. 当前设计如何支持多实例？

目前不能完整支持。任务 Map 和 SSE 监听器都在进程内，多实例会导致查询打到另一实例时找不到任务。演进方案是把任务状态和队列放到 Redis/消息队列，Worker 执行审查，事件通过 Pub/Sub 广播，并让 API 实例无状态化。

#### 28. SQLite 同步 API 会有什么问题？

同步查询会阻塞 Node.js 事件循环。当前写入量低、记录小，换取了简单部署；如果并发和数据量上升，应采用异步客户端、连接池和迁移工具，或迁移到 PostgreSQL。

#### 29. 服务崩溃后任务如何恢复？

当前无法恢复，因为任务状态和原始 Diff 不持久化。这是隐私与可靠性之间的取舍。若需要恢复，应加密持久化任务载荷、设置短 TTL、限制访问，并由可靠队列管理重试和幂等。

### 测试、部署与工程质量

#### 30. 单元测试、评测和冒烟测试有什么区别？

单元/接口测试验证具体函数和 API 边界；确定性评测验证一组样本上的规则集合、召回和意外命中；冒烟测试验证构建后的生产 bundle 在隔离环境中能启动并走通 HTTP、任务、历史和导出主链路。三者覆盖层次不同，不能互相替代。

#### 31. 为什么评测样本必须完全虚构？

评测样本会长期进入 Git 和 CI，真实公司代码、内部域名或凭据一旦提交很难彻底清除。虚构的最小样本既能验证行为，又避免把敏感数据扩散到仓库、CI 日志和模型上下文。

#### 32. 生产 bundle 冒烟为什么复制到临时目录？

如果直接在仓库运行，程序可能意外依赖根目录的 `node_modules` 或源码。复制单一 bundle 到隔离目录，可以验证构建产物确实自包含，并更接近容器运行环境。

#### 33. Docker 为什么使用多阶段构建？

Builder 阶段安装开发依赖并构建；Server 运行阶段只复制 bundle，Web 阶段只复制静态资源和 Nginx 配置。这样减小运行镜像、减少攻击面，也避免把源码和构建工具带入生产容器。

#### 34. Nginx 为什么设置 `proxy_buffering off`？

SSE 需要事件尽快传到浏览器。开启代理缓冲可能让多个进度事件积累后一起发送，看起来像没有实时更新。

#### 35. 这个项目上线前最需要补什么？

优先级最高的是鉴权、资源所有权、限流、HTTPS 和审计日志；其次是持久任务队列、多实例一致性、数据库迁移与备份、可观测性、真实模型质量评测和成本控制。当前 Compose 默认只绑定 `127.0.0.1`，就是因为这些公网服务能力尚未补齐。

#### 36. 项目最值得讲的故障或修复是什么？

可以讲三个隐私加固案例：任务 ID 与历史 ID 复用会形成跨资源读取风险；风险证据截断后可能绕过完整行精确替换；只替换分块头路径无法覆盖代码字符串中的真实路径。它们分别通过独立 ID、历史 evidence 统一隐私化，以及最终 Prompt 全量路径替换修复，并增加回归测试。
